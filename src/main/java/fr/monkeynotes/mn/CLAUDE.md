
## Seed default preferences at account creation (part 2)

- Previously preferences rows only appeared lazily, the first time a user opened the Preferences page (`listPreferences()` -> `initPreferences()` when `isParametersSet()` is false). Until then `getPreference()` threw `ServiceException("Preferences not set")` for that user, which `MonkeySyncServiceImpl.java:77` absorbed via catch-as-control-flow. Accounts are now seeded at creation instead.
- **The planned approach did not survive contact with the bean graph.** Injecting `PreferencesService` into `UserServiceImpl` closes a cycle: `UserServiceImpl` is the only `UserDetailsService` bean, `AuthServiceImpl` autowires `UserDetailsService`, and `PreferencesServiceImpl` autowires `AuthService` — giving `AuthServiceImpl -> UserServiceImpl -> PreferencesServiceImpl -> AuthServiceImpl`. Boot 3.x rejects circular references by default and nothing sets `allow-circular-references`, so that would have failed startup, not just been untidy.
- Decoupled with a spring event instead: new `data/event/UserCreatedEvent` record, published by `UserServiceImpl.createNewUser()` and by the `init_admin` bootstrap in `UtilsServiceImpl.initUsers()`; `PreferencesServiceImpl.onUserCreated()` listens and seeds. No dependency edge is added in either direction, and it covers every future caller of `createNewUser` rather than just the one controller path. Rejected alternatives: seeding from `AuthController` (leaks account setup into the controller and misses non-controller callers) and `@Lazy` (breaks the cycle with a proxy but leaves it in the graph).
- `PreferencesService` gained `isParametersSet(String username)` and `initPreferencesIfMissing(String username)`; the no-arg `isParametersSet()` now delegates to the overload with the context user, so no existing call site changed. The seeding path never touches `authService.getUsernameFromContext()` — this is required, not stylistic: the admin bootstrap runs on `ApplicationReadyEvent` where there is no security context at all, and an admin creating an account is not the account being seeded.
- Seeding is guarded by `isParametersSet(username)` because `initPreferences()` ends in a `saveAll()` that overwrites by primary key — unguarded, a re-run would silently reset a user who had already configured themselves.
- `createNewUser` is now `@Transactional`, so the user row and its preference rows commit together; the listener is synchronous and joins that transaction. Consequence worth knowing: if seeding fails, user creation rolls back rather than leaving a half-provisioned account.
- Kept the lazy `initPreferences()` path in `listPreferences()` deliberately. It still covers users created before this change, and `UtilsServiceImpl.deleteAllData()` calls `repositoryConfig.deleteAll()`, wiping every user's preferences while leaving the users themselves intact.
- No backfill of existing users was included — it was raised as an open question and never settled, so existing accounts still rely on the lazy path.
- Verified: `mvn compile` clean, and the injection graph of all 39 beans parsed and checked for cycles (0 found; `UserServiceImpl` has no edge to `PreferencesServiceImpl`). The counterfactual was also checked — modelling the direct injection reproduces the `AuthServiceImpl -> UserServiceImpl -> PreferencesServiceImpl -> AuthServiceImpl` cycle, confirming the event is load-bearing. Not run against a live context: no test sources exist and starting the app with `init_admin` active would have called `repositoryUser.deleteAll()`.
